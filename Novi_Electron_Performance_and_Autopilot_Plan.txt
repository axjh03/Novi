NOVI ELECTRON PERFORMANCE REVIEW AND AUTOPILOT IMPLEMENTATION PLAN
Date: October 15, 2026
Scope: Research and code review; no implementation changes.

SUMMARY

Novi can support hands-free interview answers. The biggest gaps are in the audio-to-answer flow. This review found no evidence that replacing Electron is necessary.

The app already captures microphone and system audio separately, supports streaming local transcripts and optional speaker labels, and streams answers from the selected AI provider. The assumed workload is one live interview on a laptop.

1. WHAT IS HOLDING THE APP BACK

1.1 Cloud transcription buffers clips instead of continuously streaming

CloudListening collects audio until 800 ms of silence or five seconds of audio, then uploads a WAV. Requests share a serial queue, so a slow request delays the next one, including the other audio source. When the queue fills, audio is skipped.

Fix: Add a persistent streaming speech connection for live interviews. Keep WAV transcription for recordings. Otherwise, autopilot inherits delayed or incomplete questions.

Code: src/renderer/src/services/cloudListening.ts:29

1.2 Some local models repeatedly reprocess audio

The Whisper/Parakeet path decodes a rolling four-second window every second, then decodes the full utterance when it finishes. On a slower CPU, that competes with incoming audio.

Fix: Use a true streaming recognizer by default for live interviews. Benchmark offline models separately for accuracy. Sherpa supports both approaches, so replacing the speech stack is unnecessary.

Code: src/main/services/localSpeechRuntime.ts:38
Source: https://k2-fsa.github.io/sherpa/intro.html

1.3 A finished speech segment is not necessarily a finished question

Segments currently end through recognizer endpointing, silence, or a 20-second limit. A pause in "Design a cache... that works across regions" could split one question into two. Automatically sending every final transcript would produce premature answers.

Fix: Add a separate decision layer that groups transcript segments into complete questions and recognizes follow-ups. Do not use transcript finalization alone as the auto-send trigger.

Code: src/main/services/interviewEngine.ts:55

1.4 Sending cannot yet manage automatic follow-ups

Transcripts populate the composer, but sending requires an action. Another send is blocked while an answer is generating. Simply calling submit() automatically would miss questions arriving during generation.

Fix: Introduce explicit handling for new questions, clarifications, and interruptions. Queue, merge, or cancel as appropriate. Keep listening while an answer streams.

Code: src/renderer/src/components/chat/Composer.tsx:292

1.5 Speaker labels do not establish reliable identity

Microphone audio is classified as the candidate; system audio as the interviewer. Optional speaker clustering runs after a system-audio segment finishes. It cannot split overlapping voices or a speaker change within one segment. Short utterances fall back to a generic label.

Fix: Use audio-source separation first and speaker clustering as supporting evidence. Do not delay a clear remote question while waiting for a named speaker. Short follow-ups such as "Why?" need contextual interpretation even without a confident speaker identity.

Code: src/main/services/interviewSpeakers.ts:9

1.6 Long-session context can grow unnecessarily

Full history and source documents are included unless compact context is requested. A compact-context path exists, but this review found no renderer control using it.

Fix: Preserve the current question, constraints, recent exchanges, and relevant resume/source facts. Avoid blindly growing every request. Validate answer quality before enabling smaller context by default.

Code: src/main/services/requestContext.ts:13

1.7 Rendering and storage deserve profiling

Each answer delta updates conversation state. Finalized transcripts are synchronously written and flushed to disk before the renderer is notified. These are possible sources of stutter, not measured causes yet.

Fix: Batch visual updates and move durable writes off the main thread without losing ordering or recovery guarantees. Measure before making larger storage changes.

Code: src/renderer/src/hooks/useChat.ts:23
Code: src/main/services/interviewStore.ts:35
Source: https://github.com/electron/electron/blob/main/docs/tutorial/performance.md

2. PROPOSED AUTOPILOT FLOW

System audio + microphone
    -> Streaming transcription
    -> Source / speaker attribution
    -> Complete question or follow-up detection
    -> Merge, queue, or cancel
    -> Stream an answer for the current mode
    -> Continue listening

Use one shared autopilot controller around the existing speech and chat services. Reuse the current mode-specific instructions rather than creating separate audio pipelines for each mode.

3. REQUIRED AUTOPILOT BEHAVIOR

- System audio triggers answers. Microphone audio provides context about what the user actually said.
- Recognize requests, not only question marks. "Explain your approach" and "Tell me about a conflict" both call for answers.
- Ignore acknowledgments such as "Okay," laughter, and "mm-hmm."
- Resolve follow-ups against the current discussion. "Why that database?" refers to the existing design. "What if traffic doubles?" updates its assumptions.
- Distinguish suggested AI answers from actual candidate speech. Do not assume the candidate said something simply because Novi generated it.
- Show understandable states: Listening, Question detected, Answering, and Waiting for clarification.
- Keep pause and Answer now controls available.
- Keep listening during generation. A real correction may cancel an obsolete answer; an acknowledgment should not.
- Avoid duplicate answers when partial transcripts are revised or finalized.
- Treat uncertain or incomplete questions conservatively rather than repeatedly firing requests.

Headphones provide the most reliable microphone/system separation. A shared room microphone or mixed speakerphone audio requires more sophisticated separation. Overlapping speech remains an uncertain case.

4. BEHAVIOR BY MODE

Q&A / Technical:
Lead with a direct answer, then stream an explanation and example.

Behavioral / Recruiter:
Use supplied experience. Answer follow-ups directly without restarting the entire story. Do not invent resume facts.

Coding:
Collect the problem and constraints before generating. Revise the answer when constraints change.

System Design:
Track requirements and assumptions. Update diagrams only when the architecture changes.

Local Coding:
Answer against the selected project. Avoid restarting an expensive agent run for every short utterance. Preserve the existing read-only project workflow.

5. TECHNOLOGY OPTIONS

Recommended first implementation:
Reuse the existing local streaming transcription and add question/turn detection above it. This is the smallest path that uses the current architecture.

Cloud option to prototype: Deepgram Flux
Flux exposes end-of-turn events, an early-generation event, and a speech-resumed event. This supports preparing an answer early and cancelling it when the interviewer continues. Novi still needs its own question and follow-up logic.

Sources:
https://developers.deepgram.com/docs/flux/configuration

Alternative/reference: LiveKit turn detection
LiveKit combines conversational meaning with voice-activity detection. Evaluate the detector or integration without migrating the entire application solely for this feature.

6. IMPLEMENTATION ORDER

Phase 1: Establish measurements
Measure audio capture, transcript availability, question completion, request dispatch, first useful answer text, and visible rendering. Separate provider latency from local processing latency.

Phase 2: Improve streaming transcription
Prefer a suitable streaming local recognizer. Prototype a persistent cloud speech connection. Keep audio queues bounded and report skipped audio clearly.

Phase 3: Detect complete questions
Combine voice activity, transcript meaning, source attribution, and recent conversation context. Group transcript segments into turns. Recognize commands and follow-ups, not only interrogative sentences.

Phase 4: Add automatic send and interruption handling
Maintain one authoritative controller for pending questions and active answers. Merge clarifications, queue genuinely separate questions, cancel obsolete generation, and prevent duplicate sends. Keep manual override available.

Phase 5: Optimize context and rendering
Preserve important constraints and source facts while reducing unnecessary request size. Batch UI updates and remove blocking persistence from the latency-sensitive path without weakening durability.

7. SUCCESS CRITERIA

Initial target: first useful answer text approximately 1-2 seconds after a completed question, under a tested hardware/network/model configuration.

This is a proposed target, not a measured result or guarantee.

Track:
- Time from question completion to first useful displayed answer.
- Typical latency and slow-tail latency.
- False triggers on acknowledgments, noise, and candidate speech.
- Missed questions and follow-ups.
- Premature answers during pauses.
- Duplicate answers after transcript revisions.
- Audio frame drops and transcription queue depth.
- Correct handling of interruptions and changing constraints.
- Answer quality with reduced context.

8. REVIEW LIMITATIONS AND VALIDATION

Six existing interview tests passed. They exercise simulated recognition, transcript lifecycle, source attribution, speaker-clustering behavior, bounded audio frames, and related protections. They do not establish real-device speed or acoustic accuracy.

Not measured: live provider performance, real microphone/system capture latency, actual speaker recognition accuracy, or hardware-specific inference speed.

No code was changed as part of this research review.

VERDICT

Keep Electron. Build a shared autopilot controller using the existing speech and chat services. Address buffered transcription and question boundaries before enabling automatic sending.
